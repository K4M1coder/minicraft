# B1 — inventaire et conteneurs serveur (L43, SPEC-SYNC-007 à 017)

Objectif : le serveur devient la seule source de vérité pour l'inventaire,
l'équipement, la grille de fabrication et le contenu des conteneurs, avec
prédiction client et réconciliation, SANS régression pour le solo ni pour un
joueur honnête en ligne (reconnexion, redémarrage `--monde`).

Lire d'abord : [README](README.md) (zones, fusion), `src/contrats-vague2.js`
(formes et messages — figés), SPECS.md § L43 (textes corrigés par ce plan).

## 3. Module pur `src/conteneurs.js` — `MC.Conteneurs`

Chargé après `inventory` ; lit `MC.Core`, `MC.Inventory`, `MC.ContratsV2` à
l'appel. Mêmes fonctions pour le solo, le client en ligne (prédiction) et le
serveur.

```js
// état d'un joueur local, partout le même :
//   { inv: Inv(36), equip: { casque, plastron, jambieres, bottes, bijou } (piles|null), grille: Inv(9) }
creerConteneur(type)            // → { type, taille, slots:[null…], four?:{burn:0,cook:0}, rev:0 }
accepteCase(cont, i, pile)      // four : 0 = entrée (Inv.smeltResult>0), 1 = combustible (Inv.fuelValue>0), 2 = sortie (jamais) ; autres : vrai
appliquer(ctx, op)              // → { ok:true, modifs:{ inv, equip, grille, conteneurs:[cle] }, effets:{…} } | { ok:false, motif }
tickFour(cont, dt)              // adaptateur sur Inv.tickFurnace ({input,fuel,output,burn,cook}) → vrai si changé
diff(avant, apres)              // slots → [[i, case]] (ContratsV2.pileVersCase)
instantane(cont) / restaurer(cont, inst)
creerPrediction()               // file d'opérations en attente (voir § 6)
versEnregistrement(joueur, banque) / depuisEnregistrement(joueur, banque, rec)   // ContratsV2.validerEnregistrementJoueur
declarer(inv, cont, slotsDeclares)                                               // DISTRIB (SPEC-SYNC-017)
TRANSFORMATIONS                 // [[I.SEAU_EAU, I.SEAU], [I.SEAU, I.SEAU_EAU]] — la seconde exige ctx.eauProche()
```

`ctx = { joueur, conteneur(cle) → cont|null, regles:{ blocsIllimites }, stats?:{ faim, vie, vieMax }, eauProche?() }`.
C'est l'appelant qui décide de l'accès : côté serveur `conteneur(cle)` ne
renvoie un conteneur que si le joueur y est abonné ET à portée (revérifiée à
chaque opération) ; `'banque'` renvoie la banque du joueur, `'grille'` n'est
jamais un conteneur (zone `grille`).

Opérations (`op.k`), toutes atomiques (tout vérifier, puis muter) :

| `k` | Champs | Règle |
|---|---|---|
| `transfert` | `de`, `vers` (emplacements du contrat), `n` | source S ≥ n ; destination vide → déplace n (scinder une pile à `dmg`/`data` interdit sauf n = S.n) ; même objet sans `dmg`/`data` et D.n + n ≤ `maxStack` → fusion ; objet différent → échange seulement si n = S.n et `accepteCase` des deux côtés ; sinon `plein`/`incompatible` |
| `craft` | `fois` (1-64) | à chaque tour : `Inv.matchRecipe(ids de la grille, 3, 3)` ; aucune → arrêt ; −1 par case non vide ; `inv.add(résultat)` ; si le 1ᵉʳ tour échoue → refus (`recette` ou `plein`), sinon `ok` avec `effets.fois` réalisés — un tour qui ne rentre pas est annulé en entier |
| `equip` | `slot`, `i` | S = inv[i], E = equip[slot] ; tous deux vides → `absent` ; S non vide et `C.def(S.id).equipSlot !== slot` → `incompatible` ; S.n > 1 → `quantite` ; échange |
| `consommer` | `ops` (contrat) | chaque op indépendante (diminution sûre) : case i porte `id` et ≥ n → `consumeAt` ; `usure` → `wearTool` ×k ; `vers` → seulement une paire de `TRANSFORMATIONS` ; une op impossible est ignorée et le résultat est `ok:false, motif:'absent'` si AUCUNE n'a pu s'appliquer, `ok:true` avec `effets.ignorees` sinon |
| `manger` | `id`, `i?` | case i (ou 1ʳᵉ case portant `id`) ; `C.def(id).food` requis ; même règle de satiété que `player.useOn` (faim pleine et pas de soin utile → `interdit`) ; −1 ; `rend` ajouté (sinon `effets.lache`) ; `effets = { food, soin, cru }` |
| `lacher` | `i`, `n` | `consumeAt(i, n)` → `effets.lache = pile` (l'appelant la fait tomber) |
| `creatif` | `i`, `id`, `n` | `regles.blocsIllimites` sinon `creatif` ; case i ← { id, min(n, maxStack) } |
| `rendreGrille` | — | chaque pile de la grille → `inv.add` ; reliquat dans `effets.reste` |
| `declarer` | `cle`, `slots` | par objet : ajout prélevé dans `inv` (tronqué à `inv.count`), retrait rendu à `inv` (le non-casé reste dans le conteneur) ; Σ(inv + conteneur) conservée par id |

Exemple :
```js
var ctx = { joueur: js.etat, conteneur: function (cle) { return abonneA(js, cle) ? registre.get(cle) : null; },
            regles: regles };
MC.Conteneurs.appliquer(ctx, { k: 'transfert', de: { z: 'inv', i: 3 }, vers: { z: 'cont', cle: '10,64,-2', i: 0 }, n: 16 });
// → { ok: true, modifs: { inv: true, equip: false, grille: false, conteneurs: ['10,64,-2'] }, effets: {} }
```

## 4. Messages (formes exactes : `src/contrats-vague2.js`)

| Message | Sens | Champs | Réponse / diffusion |
|---|---|---|---|
| `CRAFT` `craft` | c→s | `j, seq, fois` | `INV_MAJ` (ack) |
| `EQUIP` `equip` | c→s | `j, seq, slot, i` | `INV_MAJ` ; `EQUIP_VU` aux autres à < 96 blocs |
| `EQUIP_VU` `equip_vu` | s→c | `id, j, slot, objet` (0 = vide) | — ; aussi à l'arrivée d'un joueur, pour chaque emplacement non vide des présents |
| `CONTENEUR_OUVRIR` `cont_ouvrir` | c→s | `j, seq?, x,y,z` ou `j, eid` | `CONTENEUR_ETAT` si accepté ; refus silencieux (ou `INV_MAJ` de refus `portee` si `seq`) |
| `CONTENEUR_ETAT` `cont_etat` | s→c | `j, cle, type, rev, slots, four?` | — |
| `CONTENEUR_FERMER` `cont_fermer` | c→s | `j, cle, seq?` (`seq` exigé pour `grille`) | `grille` : `INV_MAJ` (contenu rendu) |
| `CONTENEUR_TRANSFERT` `cont_transfert` | c→s | `j, seq, de, vers, n` | `INV_MAJ` (avec `conteneurs:[delta]`) à l'auteur ; `CONTENEUR_MAJ` aux autres abonnés |
| `CONTENEUR_MAJ` `cont_maj` | s→c | `cle, rev, maj:[[i, case]], four?` | — |
| `INV_CONSOMMER` `inv_consommer` | c→s | `j, seq, ops` (≤ 16) | `INV_MAJ` (ack) |
| `INV_LACHER` `inv_lacher` | c→s | `j, seq, i, n` | `INV_MAJ` ; objet au sol (`entites.dropItem`, délai de ramassage) |
| `INV_CREATIF` `inv_creatif` | c→s | `j, seq, i, id, n` | `INV_MAJ` (refus `creatif` en survie) |
| `INV_MAJ` `inv_maj` | s→c | `j, rev, ack, inv, equip, grille, refus?, conteneurs?, gain?` | — |
| `MANGER` (existant) | c→s | + `i?`, `seq?` | `INV_MAJ` si `seq` |
| `DISTRIB` (existant) | c→s | inchangé | sémantique SPEC-SYNC-017 |
| `DONNE` (existant) | s→c | inchangé | ne sert plus qu'au retour visuel/sonore : le client n'ajoute PLUS rien sur `DONNE` |

Ordre et idempotence : par connexion et joueur local, `seq` strictement
croissant (1, 2, …), `js.dernierSeq` côté serveur ; un message de `seq` ≤
`dernierSeq` est ignoré (ni effet ni réponse) ; `ack` = `dernierSeq`. TCP
garantit l'ordre ; une connexion neuve repart à `seq` 1 (le serveur remet
`dernierSeq` à 0 à `REJOINDRE`). `rev` de l'`INV_MAJ` : +1 à chaque envoi
pour ce joueur local ; `rev` d'un conteneur : +1 à chaque modification ; un
client ignore tout `rev` ≤ au dernier connu, et rouvre (`CONTENEUR_OUVRIR`) s'il
voit un trou (`rev` > connu + 1).

Raccordement au protocole (étape 1) — dans `src/net-protocol.js`, exactement :
```js
// après la déclaration de `var MSG = { … };`
if (MC.ContratsV2) Object.keys(MC.ContratsV2.MSG).forEach(function (k) { MSG[k] = MC.ContratsV2.MSG[k]; });
// dans valider(), case MSG.MANGER :
case MSG.MANGER: return MC.ContratsV2 ? MC.ContratsV2.validerManger(msg) : (estEntier(msg.id) ? { t: msg.t, id: msg.id | 0, j: joueurLocal(msg.j) } : null);
// dans valider(), default :
default: return MC.ContratsV2 ? MC.ContratsV2.valider(msg) : null;
```
`contrats-vague2` est déjà chargé avant `net-protocol` partout. Les suites
d'intégration qui chargent `net-protocol.js` SEUL (integration-*.js) restent
valides : sans contrat, rien ne change.

## 6. Client : prédiction, réconciliation, interface

- `MC.Conteneurs.creerPrediction()` → `{ suivant(op) → seq, confirmer(ack), enAttente(), rejouer(etatConfirme, conteneursConfirmes) }`.
  `game.js` : une par joueur local (`j.predInv`), à côté de `j.prediction`.
- `operer(j, op, msg)` (game.js) : hors ligne → `MC.Conteneurs.appliquer`
  sur l'état réel ; en ligne → `seq = pred.suivant(op)`, application
  immédiate à l'état affiché, `net.envoyer(msg + seq)`.
- `onInvMaj(m)` : `ContratsV2.validerInvMaj` ; ignorer si `rev` ≤ dernier ;
  état confirmé ← message (et deltas `conteneurs`) ; `pred.confirmer(ack)` ;
  état affiché ← confirmé + rejeu des opérations en attente — écrit **en
  place** (`inv.load(cases)`) pour garder l'identité des objets tenus par l'UI.
- Conteneurs ouverts : `Map cle → { confirme, rev }` ; affiché = confirmé +
  opérations en attente qui le touchent.
- `ui.js`, modèle « pile en main » conservé à l'écran mais **plus aucun objet
  n'est réellement en main** : `heldStack` devient `{ origine: emplacement, n }`,
  l'origine s'affiche diminuée de n. Poser tout/une unité/fusionner/échanger
  = une opération `transfert` depuis l'origine (échange : seulement si n =
  pile entière ; après l'échange, la main représente la pile déplacée, même
  origine). Un emplacement d'équipement comme origine ou cible = `equip`
  (origine `inv` seulement). Clic sur le résultat = `craft {fois:1}`
  (maj+clic : `fois` max) — le résultat va dans l'inventaire, plus dans la
  main, **hors ligne comme en ligne**. Fermer : rien à rendre de la main ;
  la grille → `CONTENEUR_FERMER {cle:'grille'}` / `rendreGrille`.
  `poserRecette` (livre) = une suite de `transfert` inv → grille.
- `player.js` : les consommations passent par deux fonctions internes
  `consommerCase(i, n)` et `userCase(i)` (et `transformerCase(i, vers)` pour le
  seau) qui mutent l'inventaire ET, si `pl.journalInv` est un tableau, y
  poussent l'opération ; le repas (`useOn` → `'eat'`) ne journalise pas
  (c'est `MANGER` qui porte l'information).
- Journal → une entrée de prédiction **au moment même** de la consommation
  (pas en fin d'image) : la 1ʳᵉ consommation d'une image crée l'entrée
  `consommer` (seq s), les suivantes s'y ajoutent (16 max, puis une nouvelle
  entrée) ; l'envoi groupé a lieu en fin d'image. Sinon un `INV_MAJ` arrivé
  entre la consommation et l'envoi l'effacerait.
- Ramassage en ligne : seulement par `INV_MAJ` (`gain` pour le toast) ;
  `onDonne` ne fait plus `pickUp`.
- Touche « lâcher » en ligne : `INV_LACHER` + prédiction `lacher`, jamais
  `entities.dropItem` local.
- `EQUIP_VU` → `net.distants[cle].equip[slot] = objet` (affichage sur
  l'avatar distant si le rendu sait déjà dessiner l'équipement local ; sinon
  simplement conservé).
- `doSave` refuse en ligne ; à la connexion, l'inventaire/équipement solo est
  sérialisé dans `g.inventaireSolo` et restauré à la déconnexion.

## 7. Serveur

- Registre des conteneurs : `Map cle → conteneur` + `abonnes: Map cle → Set('id/j')`.
- Registre des joueurs nommés : `Map cleRegistre(nom, j) → enregistrement`
  (contrat). `REJOINDRE` : si la clé n'est tenue par aucun joueur connecté,
  l'état est restauré (sinon joueur éphémère, jamais enregistré) ; sinon
  inventaire vide, ou `MC_TEST_INV` (voir § 10). `fermer()` : rangement.
- Coffre de donjon : 1ʳᵉ ouverture d'un `chest` dont `monde.butinCoffre(x,y,z)`
  est non nul et absent de `monde.coffresPilles` → rempli, clé ajoutée.
- Bibliothèque générée (non posée par un joueur) : livres du monde comme
  `game.js` l. 1755-1762 (`MC.Livres` est déjà dans `MODULES`).
- Bloc conteneur cassé (`case BLOC`, `avant` de type conteneur) : tout son
  contenu tombe au sol, conteneur et abonnements supprimés (généralise le code
  du distributeur l. 964-971).
- Fourneaux : `tickFour` sur les fourneaux actifs dans le bloc `accEau` ;
  aucun message sans abonné (SYNC-016) ; avec abonnés, slots changés au tic,
  progression ≤ 2 Hz (SYNC-015).
- Ramassage : `js.joueur.pickUp(id, n, data)` côté serveur ; reliquat → au sol ;
  `envoyerInvMaj(… gain)` ; `DONNE` gardé pour le son.
- `etatMonde` : `conteneurs: [validerConteneurPersiste…]`, `joueurs: [[cle,
  enregistrement]…]` (connectés compris, instantané) ; `appliquerEtatMonde` :
  les recharge, champs absents = vides (anciennes sauvegardes v1/v2 : aucune
  conversion, `v` reste 2).
- Anti-flood : ajouter les types c→s du contrat à `FLOOD_TYPES_PAR_JOUEUR`
  avec `MC.ContratsV2.BUDGETS_FLOOD` ; un message d'inventaire ignoré pour
  débit → `refuserOp(c, j, seq, 'debit')`.

## 12. Pièges connus

- `Inv.serialize` n'écrit `dmg` qu'en 3ᵉ position et `data` en 4ᵉ : utiliser
  `ContratsV2.pileVersCase`/`caseVersPile`, jamais un format maison.
- `player.utiliserSeau` affecte directement `pl.inv.slots[pl.selected]`
  (l. 370) : invisible pour tout journal — passer par `transformerCase`.
- `ui.js` garde des références aux objets `inv` : ne jamais remplacer
  `player.state.inv` par un nouvel objet à la réconciliation (`load` en place).
- Écran partagé : jusqu'à 4 joueurs locaux sous UN nom ; clé de registre
  `cleRegistre(nom, j)` ; les `seq` sont par joueur local.
- Deux connexions sous le même nom : la seconde est éphémère (pas
  d'écrasement du registre).
- Le client en ligne ne simule plus ramassage ni fourneaux (`frame`
  l. 2354-2365, 2386, 2404) : ne pas les faire tourner deux fois.
- `closeUI`/`dropLeftovers` (l. 1981-2000) rendaient la main et la grille au
  sol : en ligne, plus rien n'est « en main », la grille se rend au serveur.
- `integration-*.js` chargent `net-protocol.js` seul : le raccordement doit
  rester neutre sans `MC.ContratsV2`.
- `armureReduction` (player.js l. 142) ne lit que `pl.equip` : côté serveur il
  devient enfin effectif — vérifier que les dégâts PvP/PvE attendus par
  `integration-pvp.js` tiennent compte de l'armure (joueurs de test nus).
- Ne pas oublier `seq` dans `CONTENEUR_FERMER {cle:'grille'}` (le contrat le
  refuse sinon).
